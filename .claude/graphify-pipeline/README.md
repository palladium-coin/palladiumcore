# graphify pipeline

Builds a knowledge graph of this repository (code, tests, documentation, library membership)
for Claude Code. The graph itself, `graphify-out/`, is **not tracked in git**: it is rebuilt from the
files in this directory, in about one minute and without spending any model tokens.

## Requirements

| What | Version used | Notes |
|---|---|---|
| graphify (`graphifyy` on PyPI) | **0.9.108** | pinned in `refresh.sh`; install with `uv tool install graphifyy==0.9.108` |
| `uv` | 0.10.4 | `refresh.sh` calls `uv tool run` |
| Python 3 | 3.12 | `strip_annotations.py` runs with plain `python3 -I` (standard library only) |
| `git` | any | the stripped copy is made from `git ls-files`, so untracked files are not in the graph |

Do not use another graphify version without rebuilding and checking the graph: the parser,
the id format and the clustering can change between releases. To try one on purpose:
`GRAPHIFY_VERSION=<x.y.z> .claude/graphify-pipeline/refresh.sh`.

## Rebuild

```bash
uv tool install graphifyy==0.9.108      # once per host
.claude/graphify-pipeline/refresh.sh    # ~1 minute, no tokens
```

The result is installed in `graphify-out/` (`graph.json`, `GRAPH_REPORT.md`, `graph.html`,
`buildsys.json`; the first, unstripped graph is kept in `raw/graph.raw.json`). `graphify-out/` has to be
kept out of git on each clone, for example with `echo graphify-out/ >> .git/info/exclude`.

After changing code, run `refresh.sh` again. **Do not run `graphify update .`**: it parses the raw
sources, where `EXCLUSIVE_LOCKS_REQUIRED(...)`, `NODISCARD` and `Q_OBJECT` make the parser drop or fuse
function names (for example `ContextualCheckBlockHeader`, `AcceptToMemoryPoolWithTime`).

## Reproducibility

Checked once: a fresh clone of the branch rebuilt with `refresh.sh` gave a graph identical to the one
built in the working tree (22,446 nodes, 53,164 edges, same community names; no node or edge on one side only).
That was on the same machine, with graphify already installed. Not checked: a host without `uv` or
graphify, or with another user/home directory.

The same graph comes back only if all of these are the same:
- **the source files** (the graph describes the commit it is built from);
- **the graphify version** (0.9.108);
- **the pipeline files in this directory**.

The build writes only to `$HOME/.cache/graphify-clean/<repo name>/` (override with `GRAPHIFY_CLEAN_DIR`)
and to `graphify-out/`; it never modifies the sources.

## What each file does

| File | Role |
|---|---|
| `refresh.sh` | entry point: strip -> build -> labels -> install |
| `strip_annotations.py` | copies the tracked tree and blanks what the parser cannot read, keeping every line and column in place. Groups: `annot` (thread-safety and Qt macros), `misc` (Qt namespace macros, `UNUSED`, `__declspec`, `asm`), `cond` (first branch of `#ifdef/#else` in the files of `first_branch_files.json`), `boost` (`BOOST_AUTO_TEST_CASE(name)` becomes `void name()`). Also writes `.graphifyrc` (`language.h=cpp`) and takes the exclusion list from `graphifyignore` |
| `graphifyignore` | what is left out of the graph: images, translations, test data, fuzz corpus, `depends/`, `build_msvc/`. The vendored subtrees (`leveldb`, `secp256k1`, `univalue`, `crc32c`) are included again by `refresh.sh` |
| `first_branch_files.json` | files where conditional compilation splits a statement (`src/netbase.cpp`, `src/util/time.cpp`) |
| `build_graph.py` | AST extraction, merges `semantic.json`, builds and clusters the graph, writes `buildsys.json` |
| `build_system.py` | reads `src/Makefile.am` and `src/Makefile.*.include`: which source file belongs to which library or binary, and what links against what |
| `apply_labels.py` + `labels.json` | names the largest communities; each name is attached to an anchor node, not to a community number, because numbers change between builds |
| `semantic.json` | the documentation layer (see below) |
| `merge_semantic.py` | merges documentation extraction chunks into `semantic.json` |

## Documentation layer

`semantic.json` holds concept nodes extracted from `doc/`, `CHANGELOG.md` and the READMEs, linked to
code symbols (for example `doc/palladium-consensus.md` -> `LwmaCalculateNextWorkRequired()`). It came from
an extraction run with Claude Code subagents (about 536,000 tokens) and is **not regenerated by
`refresh.sh`**. When the documents change, the layer is out of date until the documents are extracted
again with the graphify skill; then `merge_semantic.py <chunk dir> <graph.json> semantic.json` rebuilds the file.
Some files were only partly read by the subagents (`CONTRIBUTING.md`, three READMEs); see `history.md`.

## Hooks

`graphify install --project` also registers hooks in `.claude/settings.json`. They call
`graphify hook-guard` and fail on a host where `graphify` is not on the `PATH`, so they are not part of
the committed files. On a host that has graphify, run `graphify install --project` to create them.

## Known limits of the graph

- `path` can take a shortcut through a file node (two functions in one file are two hops apart): check a call chain one hop at a time.
- Classes have one placeholder node per file (`CTxMemPool`, `CWallet`): disambiguate with `file::symbol`.
- Calls through a temporary, such as `MemPoolAccept(pool).AcceptSingleTransaction()`, are not resolved; calls between files are INFERRED (0.85).
- Results include `src/test`, `src/bench` and the vendored code: ignore them for questions about Palladium itself.
- Low confidence: `src/netbase.cpp`, `src/util/time.cpp`, `src/tinyformat.h`, `src/palladium-cli.cpp`, `src/qt/`, and the four files that still fail to parse (`src/crypto/sha256_sse4.cpp`, `src/palladium-cli.cpp`, `src/test/arith_uint256_tests.cpp`, `src/tinyformat.h`).
